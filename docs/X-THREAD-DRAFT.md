## Post 1/10
An AI agent can hold a restricted key and still reach powerful contract behavior. How can an owner prove what it may do?

I built NEARMARK at NEAR HACKATHON with @NEARProtocol: evidence-first security inspection and payment controls for NEAR agents.

#NEARHackathon

## Post 2/10
NEARMARK reads public NEAR account and access-key evidence through NEAR JSON-RPC. It distinguishes FullAccess from FunctionCall scope, receiver, methods and allowance. FastNear history is indexed sampling, not complete forensic history.

## Post 3/10
Owners define the payment mandate. NEARMARK evaluates recipient, method and exact amount, then returns ALLOW, WARN or BLOCK with reasons. An API policy result is not itself on-chain enforcement.

## Post 4/10
The native NEAR Gate adds agent-key binding, recipient allowlists, payment and daily limits, expiry, single-use nonce protection and emergency pause. It has local NEAR Workspaces Sandbox evidence; public deployment is not claimed.

## Post 5/10
NASB-0.1 tests recipient substitution, legitimate payment, amount limit, permit binding, replay and restricted method. The recorded local deterministic run passed 6/6. This is not a wallet-safety certification.

## Post 6/10
NEAR stack: near-sdk-rs, NEAR Workspaces, near-cli-rs, FunctionCall access keys and a NEP-141 FT Gate. The FT Gate is built and tested locally, not claimed deployed.

## Post 7/10
NEAR AI: attestation-aware inference adapter; a prior provider_tee inference was verified. OutLayer: WASI receipt worker with TDX and input checks, but remote output integrity remains NOT_PROVEN.

## Post 8/10
NEAR Intents supports read-only token metadata and dry quote preview. Agent Market supports read-only service-catalogue discovery. Neither means live payment execution or a published NEARMARK listing.

## Post 9/10
Evidence is labelled confirmed on-chain, Sandbox-observed, code-inferred or unknown. NEARMARK keeps limitations visible instead of turning missing evidence into a security claim.
